# Design

## Application boundary

`ApplicationService` is the presentation-independent entry point for media probing, plan construction, preset resolution, single transforms, and batch jobs. It reports typed progress events so command-line and future terminal interfaces can share execution behavior.

Jobs accept a cloneable `CancellationToken`. Native stages and video-frame batches check it at bounded work boundaries, FFmpeg processes are killed and reaped when it is raised, and atomic sessions check it before publication. `LocalState` stores a versioned, bounded JSON history containing resolved seeds, output paths, statuses, and diagnostics.

The TUI queue distributes one file at a time through the same application transform command. Pausing blocks new intake without interrupting the active item; cancellation reaches the active codec and retains pending work for resume. Failed jobs retain their resolved seeds for retry, while snapshots expose per-file results and a bounded newest-first operational log.

Databender is one Cargo package exposing a reusable library and a thin CLI. The library owns media types, filter specifications, capability validation, pipeline planning, execution, and errors. The CLI only parses user input, invokes the library, and renders results.

## Pipeline Model

Filters belong to explicit processing domains:

- `JpegHuffmanTables` uses the versioned `table` compatibility engine to mutate AC symbols in JPEG DHT segments without reconstructing coefficient blocks.
- `EncodedPayload` operates only on adapter-supplied safe payload regions.
- `ImagePixels` operates on decoded image or video frames.
- `PcmAudio` operates on decoded, frame-aligned samples.
- `Mp3MainData` mutates parser-approved bytes in unprotected MPEG Layer III frames.
- `FfmpegAudio` and `FfmpegVideo` compile typed effects into allowlisted FFmpeg graphs.

Each codec advertises supported domains. Preflight validation checks the entire ordered filter list and groups adjacent filters with the same target and domain into stages. A stable mixing function derives a deterministic seed for each stage.

## Execution Model

JPEG, PNG, and WAV use native Rust decoders plus narrow container scanners. MP3 combines a native Layer III scanner with installed `ffmpeg` and `ffprobe`; Ogg combines a native page, lacing, packet, sequence, and CRC scanner with those tools. MP4 uses the external tools for compressed processing. `ToolRunner` constructs commands as argument arrays without a shell, nulls standard input, passes FFmpeg its supported `-nostdin` flag, drains standard output and error concurrently, and retains only configurable bounded tails. It reports launch errors and nonzero statuses distinctly. A configurable deadline defaults to 120 seconds; expired children are killed and reaped before control returns.

Format and filter discovery probes `ffmpeg`, `ffprobe`, and each adapter's required encoders through the same bounded runner. FFmpeg returns success for unknown encoder-help requests, so availability also inspects the captured diagnostic rather than trusting exit status alone. Native formats remain available independently of external tools.

`compile_audio_graph` maps only typed `AudioEffect` values to allowlisted FFmpeg filters and preserves stage order. High-pass and low-pass compile to frequency-bounded filters, echo uses fixed input/output gains plus typed delay and decay, and volume accepts only the parser's bounded gain. `compile_video_graph` similarly maps hue, equalization, and lag to bounded `hue`, `eq`, and `tmix` filters. `ToolRunner` requests structured JSON for ordered audio and video streams and counts decoded frames. Validation rejects missing or malformed streams, changes to stream counts, changes to sample rate or channel count, and changes to ordered video dimensions, average frame rates, or frame counts. The MP3 adapter alternates native main-data mutation and FFmpeg audio stages through temporary MP3 files in plan order. Native stages select budgeted bytes without replacement from targeted unprotected frames and flip a bounded number of bits using the stage seed. The adapter maps source metadata during FFmpeg stages, reparses final MP3 structure, validates stream geometry and codec, and performs a complete decode to FFmpeg's null muxer before publication.

The MP4/Matroska adapter partitions ordered stages by target stream and processes one or more explicitly selected zero-based video streams plus every audio stream. FFmpeg video stages produce independent lossless FFV1 intermediates. Image-pixel stages decode RGBA8, apply native filters in batches capped at eight frames and the available CPU parallelism, and return to FFV1. Batch roots derive tagged file seeds; native container stages then derive tagged stream, original stage, and frame seeds in hierarchy. Completed frames are joined and written in source order, and single-worker and multi-worker output is tested byte-for-byte. Each audio stream independently traverses its ordered stages as 16-bit PCM WAV: FFmpeg audio effects produce a fresh intermediate, while PCM stages apply native bounded noise to decoded samples. The final mux restores original video ordering, copies unselected video streams, and encodes processed video as MPEG-4 video for MP4 or FFV1 for Matroska; processed audio uses AAC or FLAC respectively. Before processing, the adapter snapshots an allowlist of global title, artist, album, comment, genre, date, creation time, and copyright tags plus primary-video and audio title and language. Matroska additionally maps subtitle and attachment streams plus chapters and snapshots auxiliary codecs, chapter IDs/timing, and title, language, filename, and MIME-type tags. Final validation requires the expected signature, unchanged metadata and complete video/audio stream geometry, exact Matroska auxiliary topology, then decodes every video and audio stream completely to FFmpeg's null muxer. Video-only input is accepted when no audio effect is requested. MP4 auxiliary streams remain out of scope.

The MP4 and Matroska packet-only paths probe codec-aware samples and SHA-256 packet hashes. MP4 verifies each direct `pos`/`size` range. For Matroska, a checked EBML walker locates unlaced `SimpleBlock` and `Block` payloads and resolves selected packets by forward size and hash because ffprobe positions include block framing. Both paths copy the source container, reject missing, ambiguous, or overlapping ranges, and perform equal-length writes only inside selected payloads. Per-packet seeds derive from stage, stream, and packet identities. Validation preserves topology, codec, dimensions, frame rate, metadata, audio properties, Matroska auxiliary streams, and the configured frame-loss bound, then fully decodes the candidate. Packet stages cannot mix with decoded stages.

The image executor accepts ordered JPEG Huffman/pixel stages and PNG pixel/payload stages. For baseline sequential JPEGs, Huffman stages parse SOF0, DHT, DRI, and SOS structures, decode entropy symbols MCU-by-MCU without reconstructing pixels, and count AC symbol use per table. Actual SOS component assignments classify tables as luma or chroma. Intensity scales swap count quadratically. Candidate pairs are ranked by combined observed use; low intensity draws from the lowest-impact fraction and limits run-distance changes, while higher intensity progressively broadens the pool. The default target is luma AC to avoid immediate global color scrambling. Run remapping changes zero-run meanings while preserving amplitude size; symbol remapping can optionally cross size classes for less stable corruption. Segment lengths, code counts, and entropy data remain unchanged. The explicit `table` engine preserves this behavior as a compatibility path: it globally changes DHT symbol interpretation rather than reconstructing and selectively editing coefficient blocks. Progressive or unsupported scan layouts use deterministic DHT fallback mutation rather than incomplete coefficient analysis. Pixel stages decode to RGBA8, apply adjacent filters, and re-encode to the detected input format. PNG payload stages validate all chunk bounds and CRCs, concatenate and inflate `IDAT`, preserve each non-interlaced row's filter byte, mutate only the fixed-length row payload, recompress it, and replace the original `IDAT` chunks with one correctly framed chunk. This permits transitions between domains without publishing an invalid compressed stream.

The WAV executor scans RIFF chunks with padding, validates integer PCM geometry and whole-frame alignment, and supports 8-, 16-, 24-, and 32-bit samples. PCM noise is applied per sample with deterministic probability, bounded amplitude, and saturation. Encoded-payload filters operate only on the fixed-length `data` chunk. Candidate validation reparses the output and requires the original format, data range, and every byte outside that range to remain exact.

Byte repeat copies selected bytes forward. Byte drop shifts subsequent bytes left and zero-fills the tail. Noise and swap are also length-preserving. These semantics keep scanline framing stable. Byte-only PNG pipelines preserve all non-`IDAT` chunks.

Before image execution, the codec snapshots supported metadata. Every pixel re-encode transplants that snapshot, and candidate validation extracts it again for a byte-for-byte comparison. JPEG preserves APP1 (including EXIF/XMP), APP2 (including segmented ICC profiles), and COM segments in source order. PNG preserves `cHRM`, `gAMA`, `iCCP`, `sRGB`, `pHYs`, `eXIf`, text, and timestamp chunks. Chunks tied to the original pixel layout, such as `tRNS`, `hIST`, and `bKGD`, are not transplanted. JPEG drops alpha during encoding and rejects generic payload stages during preflight.

## File Safety

`TransformRequest::prepare` canonicalizes paths, detects the input format from its content signature, and validates a complete plan before creating output. It always rejects identical input/output paths. Existing destinations are replaced by default; callers can enable output protection for race-safe no-clobber publication. `PreparedTransform::publish_with` writes candidates to a temporary file beside the destination, flushes and synchronizes them, runs adapter validation, and atomically persists them. `publish_path_with` provides the same lifecycle for external encoders that require a destination path. Failed runs leave existing files untouched.

## Presets and Batch Execution

The library loads named presets from a strict, versioned TOML schema. Version 1 stores ordered textual filter specifications, an optional seed, and a replace-or-protect output policy. Filter strings pass through the same typed parser as CLI arguments. Explicit CLI filters append after preset filters, an explicit seed overrides a preset seed, and protection can only be tightened.

`BatchRequest` recursively expands explicit files and directories, excludes regular files without a recognized case-insensitive media extension, sorts and deduplicates canonical inputs, computes all output paths, and rejects flat-layout collisions before starting workers. Retained files still undergo content-signature detection during transform preparation. Mirrored layout requires a root and rejects inputs outside it. A bounded worker set executes independent `TransformRequest` values. Seeds are derived from the base seed and canonical input path, while results are restored to sorted input order regardless of scheduling. Dry runs return the same serializable report without creating destination directories or transforming media. Item failures do not stop other scheduled work; the CLI reports each result and returns a failing aggregate status.

Batch reports are also versioned resume manifests written through a same-directory temporary file. Manifest schema v3 records pipeline plan version 1, and resume rejects either unsupported version before comparing work. The fingerprint covers the explicit plan behavior version, Databender version, resolved filters, output protection, canonical input/output mappings, per-item seeds, and streamed input bytes. Resume rejects a mismatched fingerprint before workers start. A prior success is skipped only when its exact input/output/seed tuple matches and its published output still exists; failed or missing outputs remain pending. The updated manifest records executed and resumed items separately.

## Determinism

The CLI reports generated seeds, while the library requires an explicit seed. Native stages using the same input, options, seed, and Databender version promise byte-identical output. FFmpeg-backed output may vary across FFmpeg builds; its reproducibility contract covers the resolved pipeline and parameters instead.
